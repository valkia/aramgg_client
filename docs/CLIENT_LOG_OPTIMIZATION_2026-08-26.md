# ARAMGG 客户端日志优化诊断

## 文档状态

- 记录日期：2026-08-26
- 状态：已诊断，尚未实施
- 适用客户端：`aramgg_client` 0.2.12、0.2.13
- 适用数据版本：16.16.2、16.16.3
- 日志样本：`app-2026-08-24.log`、`app-2026-08-25.log`、`app-2026-08-26.log`

本文记录三天真实客户端日志暴露的产品、性能、隐私、发布安全和可观测性问题。当前只完成只读诊断，没有修改客户端代码、生产配置或公开数据。

## 证据边界

- 只使用日志里的公开英雄、海克斯、版本、耗时和聚合计数。
- 不记录玩家名称、Riot ID、PUUID、召唤师 ID、访问令牌或其他身份字段。
- `random-floating-test`、`sources: ["mock"]` 等模拟数据不计入真实对局统计。
- 单次错误或单次内存峰值只标记为风险，不能直接证明稳定复现或内存泄漏。
- 配置超时、Analytics 请求失败和 LCU 正常退出不等于英雄海克斯胜率接口失败。

## 总体结论

客户端的核心流程整体可用：选人快照、装备写入、赛后统计、数据刷新和自动更新最终大多成功。日志未显示持续 CPU 饱和，平均 CPU 为 2.3%～4.6%，峰值为 11.6%。

当前最需要处理的四项问题是：

1. 生产环境自动保存整屏 OCR 截图并记录原始 OCR 文本，存在隐私风险。
2. Windows 自动更新发布者签名校验被明确关闭，存在供应链风险。
3. 无匹配 OCR 文本的模糊匹配耗时过高，最坏达到 12.27 秒。
4. 500ms 截图调度与实际分析能力长期不匹配，约一半调度因背压被跳过。

## 问题清单

### CL-01：生产环境保存整屏 OCR 截图和原始文本

- 优先级：P0
- 类型：隐私、安全、存储
- 证据：三天自动保存 45 张部分识别截图；日志多次记录非 LoL 应用的 OCR 文本。
- 代码位置：`src/main/auto-screenshot-service.ts`、`src/main/screenshot.ts`

当前 `preferScreenCapture=true` 时只选择屏幕源，部分识别诊断又会把完整 `imageBuffer` 写入磁盘。用户切换到其他应用时，截图和 INFO 日志可能包含与 ARAMGG 无关的屏幕内容。

建议：

1. Production 默认禁用截图落盘，仅在用户主动开启诊断模式后允许。
2. 只保存三个标题区域或经过遮罩的裁剪图，不保存整屏。
3. INFO 日志删除原始 `slotTexts`，保留槽位、匹配 ID、耗时、置信度和拒绝原因。
4. 诊断截图设置明确的过期时间、最大总大小和用户可见的清理入口。
5. 日志继续统一脱敏玩家身份、桌面路径和本地端口凭据。

验收：

- 默认 Production 连续两局生成 0 张 OCR 截图。
- INFO/WARN/ERROR 日志不包含原始 OCR 文本和玩家身份。
- 诊断模式只输出裁剪区域，退出诊断模式后立即停止落盘。

### CL-02：Windows 更新签名校验被关闭

- 优先级：P0
- 类型：发布安全
- 证据：每次启动记录 `Windows update signature verification is temporarily disabled`。
- 代码位置：`src/main/app-update-service.ts`

当前实现将 `verifyUpdateCodeSignature` 覆盖为始终成功。固定 CDN 源和更新清单哈希不能完全替代 Windows 发布者签名。

建议：

1. 完成 Windows 安装包和升级包代码签名。
2. 在客户端内置受信任发布者名称并恢复 `verifyUpdateCodeSignature`。
3. 发布流程增加签名、发布者、`latest.yml`、安装包和 blockmap 的端到端验证。
4. 未通过签名校验时拒绝安装并提供清晰错误，不自动降级为无校验安装。

验收：

- Production 启动不再出现签名校验关闭告警。
- 正确签名升级成功；篡改、未签名和错误发布者安装包均被拒绝。

### CL-03：模糊匹配在无命中路径耗时过高

- 优先级：P1
- 类型：性能、响应延迟
- 证据：多数慢帧的 OCR 只占 80～200ms，`matchMs` 却达到 1.1～1.38 秒；最坏达到 12.27 秒。
- 代码位置：`src/main/image-analyzer.ts`

当前每段 OCR 文本遍历全部多语言名称，并为大量滑动窗口创建完整 Levenshtein 矩阵。无匹配文本比精确匹配文本更慢。

建议：

1. 建立规范化名称和别名的精确索引，优先 O(1) 命中。
2. 按语言、名称长度、首字符或 n-gram 缩小候选集。
3. 编辑距离改为双行、阈值提前退出，避免二维矩阵反复分配。
4. 缓存相同标题指纹和规范化 OCR 文本的匹配结果。
5. 每帧只解析一次语言优先级和匹配索引，再传给三个槽位。

验收：

- 无匹配帧 `matchMs` P95 小于 150ms，最大值小于 500ms。
- 精确匹配不回归；三种 OCR 语言的现有样例全部通过。

### CL-04：截图调度与分析吞吐不匹配

- 优先级：P1
- 类型：性能、功耗、调度
- 证据：9,107 次分析对应 9,125 次背压跳过，约一半定时调度没有实际工作。
- 代码位置：`src/main/auto-screenshot-service.ts`

建议：

1. 使用单串行流水线或基于上一帧耗时的动态间隔，不再固定产生注定被跳过的任务。
2. LoL 不是前台窗口时暂停 OCR 或降到 2～5 秒。
3. 先运行低成本像素/界面门禁，确认可能出现海克斯选择界面后才执行 OCR。
4. 稳定识别后使用 1.2～2 秒间隔，检测到标题区域变化时短暂加速。

验收：

- 连续两局背压跳过率低于 10%。
- LoL 非前台期间不进行高频整屏截图。
- 海克斯选择界面出现后的首次有效识别不慢于现有版本。

### CL-05：浮窗清除条件过于激进

- 优先级：P1
- 类型：用户体验、状态机
- 证据：三天发生 17 次 OCR miss 清除；多次在有效识别后约 2.1～2.5 秒清除。
- 代码位置：`src/main/auto-screenshot-service.ts`

建议：

1. 稳定三卡结果不能只因两帧 miss 清除。
2. 同时满足标题区域消失、重随按钮消失和连续多帧确认后再隐藏。
3. 低置信度帧只更新确认变化的槽位，不能清空其他稳定槽位。
4. 记录同一选择轮次的 `show/update/clear` 状态，便于识别抖动。

验收：

- 同一轮选择界面不发生隐藏后重新出现。
- 界面真正关闭后浮窗在可接受时间内隐藏，不残留到正常战斗画面。

### CL-06：Electron 内存基线偏高且峰值不可定位

- 优先级：P1
- 类型：内存、架构、可观测性
- 证据：常见峰值约 0.84～1.18GB，单次达到 2.52GB；启动立即创建四个 renderer。
- 代码位置：`src/main/modules/performance-monitor.ts` 和窗口管理模块。

建议：

1. 浮窗和侧栏首次使用时再创建，未使用窗口不提前启动 renderer。
2. 对不会同时展示的窗口评估复用；需要同时展示的窗口保留独立状态。
3. 记录各 renderer、OCR 子进程、Network Service 和 GPU 进程的峰值。
4. 增加持续高内存告警和两局连续增长诊断，不只记录退出时的总峰值。

验收：

- 两局连续回归中工作集不单调增长。
- 能从日志定位峰值进程和窗口路由。
- 在不影响浮窗展示的前提下显著降低启动内存。

### CL-07：赛后 partial 使用错误英雄且 ready 重复生成

- 优先级：P1
- 类型：正确性、状态机、重复工作
- 证据：多个对局在 `WaitingForStats` 先生成错误英雄的 partial，随后由 EOG 数据修正；相同 ready 又在 `PreEndOfGame` 和 `EndOfGame` 各生成一次。
- 代码位置：`src/main/services/post-game-share.ts`

建议：

1. `WaitingForStats` 阶段不使用缓存英雄生成用户可见海报。
2. EOG 统计确认英雄后才发布 ready。
3. 按对局 ID 和内容哈希去重，同一局只生成、通知一次。
4. partial 只能显示“生成中”，不得覆盖上一局或展示未确认英雄。

验收：

- 每局最多一个 ready 事件。
- partial 与 ready 的英雄一致；无法确认时不携带英雄。
- 上一局海报不会在新一局结束时短暂回显。

### CL-08：远端配置请求缺少统一缓存和退避

- 优先级：P2
- 类型：网络、离线容错
- 证据：8 月 24 日出现 9 条 10 秒配置超时日志，数据刷新与战绩上传会分别记录失败。
- 代码位置：`src/main/data-loader.ts` 和战绩上传配置读取。

建议：

1. 统一共享最近一次成功的 config 结果和同一个在途 Promise。
2. 网络失败使用指数退避和随机抖动，避免固定频率重试。
3. 已有完整缓存数据时继续本地工作，只显示非阻塞离线状态。
4. 网络恢复后再刷新，不让多个功能同时发起相同请求。

验收：

- 离线 30 分钟期间不会每个模块分别重复请求 config。
- 恢复网络后能自动刷新到当前版本。
- 超时不影响已缓存的英雄、海克斯和出装数据。

### CL-09：差分更新失败噪声和 CDN Range 兼容

- 优先级：P2
- 类型：更新可靠性、日志语义
- 证据：0.2.13 更新多次出现 HTTP 416 和一次连接重置，最终回退全量下载成功。

建议：

1. 验证 CDN 对安装包和 blockmap 的 Range、ETag、Content-Length 响应。
2. 发布验收同时覆盖差分下载和全量回退。
3. 可预期且成功回退的差分失败记录为 WARN，而不是最终 ERROR。
4. 避免应用重启后重复执行相同失败的差分尝试。

验收：

- 同版本升级优先完成差分下载；不支持差分时只回退一次。
- 最终成功更新不会留下误导性的“更新失败”状态。

### CL-10：正常生命周期事件被记录为错误

- 优先级：P2
- 类型：日志质量、告警降噪
- 证据：League 尚未启动、正在退出或刚进入游戏时，日志会记录 LCU 连接失败、无法恢复英雄和通用 `Failed to fetch`。

建议：

1. 启动和退出阶段的 LCU 不可用降为 INFO，并增加宽限时间。
2. 只有超过宽限期且影响功能时才记录 WARN/ERROR。
3. Firebase Analytics 已知 fallback 使用单条结构化诊断，不重复输出通用 fetch 错误。
4. 为网络、LCU、数据和渲染错误增加稳定的错误码。

验收：

- 正常启动、打一局、关闭 League 的回归流程没有 ERROR。
- 真正的数据加载失败仍能通过稳定错误码定位。

### CL-11：战绩同步缺少隐私安全的最终摘要

- 优先级：P2
- 类型：可观测性、数据覆盖
- 证据：INFO 日志只显示 SGP 列表收集数量，上传器和后台批次最终结果主要在 DEBUG。

建议：

1. 每轮同步结束记录一条聚合摘要：发现、校验通过、去重、入队、上传、重试、拒绝、跳过数量。
2. 只记录补丁、平台和计数，不记录身份和比赛正文。
3. 区分配置禁用、暂时离线、没有新比赛和服务端拒绝。

验收：

- 仅凭 INFO 日志即可判断一轮同步是否成功以及为何没有上传。
- 日志不包含 PUUID、Riot ID、原始安装 ID 或比赛正文。

### CL-12：空胜率解释和覆盖仍需继续改善

- 优先级：P2
- 类型：产品体验、数据覆盖
- 证据：16.16.3 中，日志明确展示过的唯一候选组合仍有 30.8% 没有胜率。

建议：

1. 保留“场次不足”，并在说明中明确“至少 255 场后展示”。
2. 胜率为空时继续展示官方排名、Tier 和选取率，不把空值作为零分。
3. 增加不含身份的“用户实际看到哪些空组合”聚合事件，用于优先补覆盖。
4. 继续通过合规战绩上传扩大样本，不降低公开门槛。

验收：

- 所有 `winRate=null` 的海克斯都有明确原因提示。
- 推荐排序不会因空胜率被错误降为零或误导成 0% 胜率。

## 建议实施顺序

### 第一批：隐私与发布安全

- CL-01 关闭生产整屏诊断截图和原始 OCR 文本。
- CL-02 恢复 Windows 更新签名校验。

### 第二批：OCR 热路径

- CL-03 优化匹配索引和编辑距离。
- CL-04 改造动态截图调度。
- CL-05 修正浮窗清除状态机。

### 第三批：正确性与资源

- CL-06 建立分进程内存诊断并按需创建窗口。
- CL-07 修正赛后 partial 和 ready 去重。

### 第四批：网络与可观测性

- CL-08 统一配置缓存和退避。
- CL-09 修正差分更新/CDN 验收。
- CL-10 调整日志严重级别。
- CL-11 增加战绩同步聚合摘要。
- CL-12 持续改善空胜率解释和数据覆盖。

## 回归验证矩阵

| 场景 | 必须验证 |
| --- | --- |
| 正常启动，不打开 League | 无错误级 LCU 噪声；隐藏窗口不提前占用不必要 renderer |
| 进入选人并开始一局 | 英雄快照与出装写入正常；OCR 只在 InProgress 工作 |
| 每轮海克斯选择 | 首次识别及时；槽位顺序正确；无隐藏/重现抖动 |
| 切换到其他应用 | OCR 自动降频或暂停；无整屏截图落盘；日志无原始屏幕文本 |
| 连续完成两局 | 每局一个正确 ready；内存不单调增长；背压率低于 10% |
| 断网后恢复 | 缓存数据可用；config 请求退避；恢复后自动刷新 |
| 客户端版本升级 | 签名校验通过；差分成功或只回退一次；最终状态准确 |
| 战绩同步 | INFO 摘要能解释收集、去重、上传或跳过结果，且无身份字段 |

## 非目标

- 不降低 255 场英雄海克斯公开胜率门槛。
- 不公开原始比赛正文、身份字段或私有统计快照。
- 不因单次 2.52GB 峰值直接宣称内存泄漏。
- 不把正常的 League 退出、Analytics fallback 或成功的全量更新回退误判成核心功能故障。
- 不在没有测试和发布验收的情况下同时重构 OCR、窗口和更新三条高风险链路。
